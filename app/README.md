# Документация backend приложения анализа насоса

Документ описывает серверную часть проекта: прием файла с показаниями двух
датчиков (давление и обороты), проверку формата, классификацию интервалов,
расчет длительностей и проверку диагностических гипотез.

Backend — учебный прототип. Пороговые значения и гипотезы ниже предназначены
для анализа подготовленных записей, а не для безопасного управления насосом
или подтверждения неисправности реального оборудования.

## 1. Состав backend

- `main.py` создает приложение FastAPI и подключает маршруты API.
- `endpoints.py` принимает загруженный файл, вызывает анализатор и преобразует
  ошибки входных данных в HTTP-ответы.
- `core.py` разбирает и проверяет JSON, классифицирует интервалы, считает
  итоговые длительности и оценивает десять гипотез.
- `../tests/test_core.py` содержит модульные тесты алгоритмов и контрольных
  наборов данных.
- `../data/` содержит демонстрационные JSON-файлы.

Backend не строит графики, не управляет насосом и не сохраняет результаты
в базу данных или файл. Ряды исходных показаний и рассчитанные интервалы
возвращаются вызывающей стороне в JSON-ответе.

## 2. Установка и запуск

Команды выполняются из корня репозитория.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install .
uvicorn app.main:app --reload
```

Для запроса к API и автоматической документации:

- `http://localhost:8000/` — проверка доступности приложения.
- `http://localhost:8000/docs` — Swagger UI.
- `http://localhost:8000/openapi.json` — схема OpenAPI.

Для запуска backend-тестов:

```powershell
python -m unittest discover -s tests -v
```

Проект требует Python 3.10 или новее. Зависимости приложения перечислены
в `../pyproject.toml`; для приема `multipart/form-data` используется
`python-multipart`.

## 3. HTTP API

### `POST /api/analyze`

Загружает один JSON-файл в поле `file` формы `multipart/form-data`, проверяет
данные и возвращает метрики и результаты гипотез.

Пример в PowerShell:

```powershell
curl.exe -X POST http://localhost:8000/api/analyze `
  -F "file=@data/01_small.json"
```

Пример успешного ответа (показаны основные поля; ответ также содержит `samples`,
`intervals`, `hypotheses` и примечания):

```json
{
  "status": "ok",
  "schema_version": "1.0",
  "dataset_id": "01_small",
  "synthetic": true,
  "sample_count": 13,
  "span_s": 12,
  "working_s": 9,
  "stopped_s": 3,
  "gap_s": 0,
  "invalid_s": 0,
  "unknown_s": 0,
  "modes_s": {
    "low": 3,
    "normal": 3,
    "high": 3
  }
}
```

Если файл не удовлетворяет требованиям, endpoint возвращает HTTP 422. FastAPI
помещает описание ошибки в поле `detail`:

```json
{
  "detail": {
    "status": "format_error",
    "category": "missing_field",
    "message": "В samples[0] отсутствует поле rpm.",
    "totals": null
  }
}
```

До успешной проверки всего файла итоговые метрики не рассчитываются и не
возвращаются. Ошибки, не относящиеся к содержимому файла (например, отсутствие
обязательного multipart-поля `file`), обрабатываются стандартными ответами FastAPI.

### `GET /`

Возвращает короткий ответ для проверки доступности:

```json
{"message": "Hello, World!"}
```

## 4. Входной JSON и валидация

Поддерживается версия схемы `"1.0"`. Обязательные поля верхнего уровня:

| Поле | Тип | Описание |
|---|---|---|
| `schema_version` | строка | Версия формата; должна быть `"1.0"` |
| `dataset_id` | строка | Идентификатор записи |
| `synthetic` | boolean | Признак синтетического набора |
| `samples` | массив объектов | Последовательность показаний датчиков |

Каждый объект в `samples` должен содержать:

| Поле | Тип | Условия |
|---|---|---|
| `t_s` | конечное число | Секунды от начала записи; `t_s >= 0`; метки строго возрастают |
| `pressure_mpa` | конечное число или `null` | Давление в МПа |
| `rpm` | конечное число или `null` | Обороты в минуту |
| `valid` | boolean | Признак достоверности измерения |

Пример:

```json
{
  "schema_version": "1.0",
  "dataset_id": "example",
  "synthetic": true,
  "samples": [
    {"t_s": 0, "pressure_mpa": 6, "rpm": 100, "valid": true},
    {"t_s": 1, "pressure_mpa": 6, "rpm": 100, "valid": true}
  ]
}
```

JSON читается как UTF-8 (допускается BOM). Дополнительные поля игнорируются.
Строки, boolean, `NaN` и бесконечности не принимаются вместо числовых значений;
boolean в Python отдельно исключен из проверки чисел. Дубликат или обратный
порядок временных меток приводит к отказу всего файла.

Используемые категории ошибки:

| `category` | Причина |
|---|---|
| `invalid_json` | Ошибка синтаксиса JSON или неподходящая кодировка файла |
| `missing_field` | Не найдено обязательное поле в объекте или выборке |
| `wrong_type` | Неверный тип, структура или не конечное числовое значение |
| `unsupported_version` | Версия схемы отличается от `"1.0"` |
| `non_increasing_time` | Отрицательная, повторная или убывающая метка времени |

Для `invalid_json` в сообщении указываются строка и столбец синтаксической
ошибки, если файл удалось декодировать. Остальные сообщения указывают поле
или индекс выборки, если это возможно.

## 5. Как считаются интервалы и длительности

Расчеты выполняются между каждой парой соседних показаний. Интервал имеет вид
`[start_s, end_s)`: длительность равна разности временных меток, а показания
берутся из левой записи. Последняя запись лишь закрывает предыдущий интервал;
отдельное время после нее не добавляется. Время до первой записи тоже не
достраивается.

Для каждого интервала правила применяются строго в следующем порядке:

1. Если `dt > 1.5` секунды, интервал классифицируется как пропуск `gap`.
2. Иначе при `valid=false`, `null` в давлении/оборотах или отрицательном
   давлении/оборотах интервал считается недостоверным `invalid`.
3. Иначе насос работает, если одновременно `rpm >= 50` и
   `pressure_mpa >= 1`.
4. Если условие работы не выполнено, интервал считается остановкой `stopped`.

Таким образом, при большом разрыве недостоверность значений слева отдельно не
учитывается: приоритет имеет пропуск. Между обычными соседними показаниями
предполагается постоянное значение левого измерения.

Для работающих интервалов режим определяется давлением:

| Режим | Условие |
|---|---|
| `low` | `1 <= pressure_mpa < 5` |
| `normal` | `5 <= pressure_mpa < 10` |
| `high` | `pressure_mpa >= 10` |

Основные метрики результата:

- `span_s` — время между первой и последней временными метками; для пустого
  массива и одной записи равно нулю.
- `working_s` — суммарное время работающих интервалов (`low + normal + high`).
- `stopped_s` — время остановок по учебному критерию.
- `gap_s` — время интервалов, признанных пропусками.
- `invalid_s` — время недостоверных интервалов, не отнесенных к пропускам.
- `unknown_s` — `gap_s + invalid_s`, то есть время с неизвестным состоянием.
- `modes_s` — длительности режимов `low`, `normal` и `high`.
- `sample_count` — количество исходных показаний.

Для корректной записи выполняются равенства:

```text
working_s = modes_s.low + modes_s.normal + modes_s.high
span_s = working_s + stopped_s + gap_s + invalid_s
unknown_s = gap_s + invalid_s
```

Массив `samples` в успешном ответе содержит разобранные исходные точки.
Массив `intervals` содержит интервалы с `start_s`, `end_s`, `duration_s`,
`state` и `mode`. Для состояний `gap`, `invalid` и `stopped` поле `mode`
равно `null`.

## 6. Проверяемые гипотезы

Поле `hypotheses` содержит десять результатов. Каждый результат включает:

- `id` и `title` — номер и название гипотезы;
- `status` — `detected`, `not_detected` или `insufficient_data`;
- `detected` — `true`, `false` или `null` соответственно;
- `message` — краткое человекочитаемое пояснение;
- `details` — примененный порог, рассчитанные величины, а для части проверок
  временные метки найденных интервалов.

Текущая реализация использует следующие критерии:

1. **Процесс промывки системы.** Ищет непрерывный интервал длительностью не менее
   300 секунд с `pressure_mpa < 5` и `rpm >= 50`. Интервалы `gap` и `invalid`
   разрывают такой участок. Для каждого найденного события возвращаются начало,
   конец, длительность и средние давление/обороты. Эта эвристика проверяет
   именно заданные в реализации условия: отдельного требования `working` или
   `pressure_mpa >= 1` у нее нет, поэтому подходящий интервал состояния
   `stopped` также может попасть в результат. Найденное событие не доказывает
   факт промывки.
2. **Аномальные остановки.** `detected=true`, если `stopped_s / span_s > 0.5`.
   В `details` также возвращаются переходы между последовательными рабочими
   интервалами и остановками. Неизвестный интервал разрывает последовательность.
3. **Предполагаемый износ оборудования.** Срабатывает, если доля остановок
   превышает 70% (`stopped_s / span_s > 0.7`) **или** доля пропусков превышает
   20% (`gap_s / span_s > 0.2`).
4. **Недостоверные данные.** Срабатывает, если `invalid_s / span_s > 0.2`.
   Пропуски в эту долю не входят.
5. **Деградация производительности.** Сравнивает показания с одинаковым точным
   значением `rpm` в первых и последних 20% временного диапазона записи. Для
   сравнения используются точки с `valid=true`, не-null и неотрицательными
   датчиками, `rpm >= 50` и `pressure_mpa >= 1`. Для каждого общего значения
   оборотов сначала усредняется давление, затем усредненные значения по общим
   оборотам усредняются между собой. Срабатывание — снижение более чем на 10%.
   В этой проверке используются сами точки измерений, а не длительности
   интервалов; соседство точки с большим пропуском само по себе ее не исключает.
   Если общих значений оборотов нет, результат — `insufficient_data`.
6. **Частые переключения режимов.** Считает переходы между разными режимами
   `low`, `normal` и `high` в последовательных рабочих интервалах. Счетчик
   сбрасывается на остановке или неизвестном интервале. Срабатывание —
   более 10 переходов в час; для часовой частоты используется полная
   длительность записи `span_s`.
7. **Низкое давление при высоких оборотах.** Ищет рабочие интервалы, где
   `rpm >= 100` и `pressure_mpa < 5`. Возвращает количество интервалов, их
   суммарную длительность, долю от `working_s` и сведения о каждом интервале.
   Гипотеза срабатывает, если найден хотя бы один такой интервал.
8. **Длительный режим high.** Срабатывает, если
   `modes_s.high / working_s > 0.5`. Если подтвержденного времени работы нет,
   доля считается нулевой.
9. **Восстановление после пропусков.** Считает пропуски и проверяет интервал,
   следующий непосредственно за каждым `gap`: он должен быть рабочим и иметь
   режим `high`. Возвращает количество таких случаев, долю от пропусков и
   временные отметки начала соответствующих интервалов.
10. **Периодичность недостоверных данных.** Находит начало каждой непрерывной
    серии интервалов `invalid`, вычисляет промежутки между началами и ищет
    группу промежутков, отличающихся от выбранного кандидата не более чем на
    10%. Паттерн считается найденным при трех или более похожих промежутках
    (то есть обычно требуется не менее четырех начал). Возвращает оценку
    периода, количество промежутков в группе и времена начал недостоверных
    серий.

При нулевом `span_s` доли по длительности равны нулю; гипотезы, основанные на
доле времени, не срабатывают. Проверка деградации без достаточных общих
значений оборотов отдельно показывает `insufficient_data`.

## 7. Значения времени и границы использования

В API все длительности и временные отметки выражены в секундах, давление — в
МПа, скорость — в оборотах в минуту. Числа и пороги заданы учебными правилами;
в частности, учебное условие «насос работает» не является эксплуатационным
стандартом.

Если `synthetic` равно `true`, ответ дополнительно содержит `data_note` о том,
что запись синтетическая. Любой успешный результат также содержит
`diagnostic_note`: гипотезы — эвристики, для реального оборудования нужны
размеченные записи, сравнение с нормальным режимом и проверка специалистом.
Найденное событие не равно установленной причине неисправности.

Анализатор обрабатывает один переданный файл за запрос. В текущем backend нет
аутентификации, хранения истории, потоковой обработки, управления устройством,
автоматического подбора порогов и подтверждения диагноза инженером. Не следует
использовать этот учебный API как систему защиты или управления насосом.

## 8. Тесты

`tests/test_core.py` проверяет:

- расчет контрольных метрик для наборов `01`–`07`, в том числе разрывов,
  недостоверных значений и граничных режимов;
- ожидаемые категории ошибок для наборов `08`–`10`;
- гипотезу о пятиминутном интервале низкого давления;
- сравнение давления при одинаковых оборотах;
- обнаружение периодичности недостоверных показаний;
- строгую границу доли остановок в 50%;
- времена событий после пропуска и низкого давления при высоких оборотах;
- отказ для boolean и слишком больших чисел в числовых полях.

Запуск:

```powershell
python -m unittest discover -s tests -v
```
